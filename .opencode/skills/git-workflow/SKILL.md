# Git workflow AiRecruiter

Использовать при подготовке commit, tag, push и PR. Скилл задаёт git-гигиену;
`AGENTS.md` и `docs/roadmap.md` остаются источником прав.

## Рамка

- Git по умолчанию выполняет владелец; исключение — явная команда заказчика.
- Без явной команды skill только готовит точные команды и текст сообщения.
- Не делать force-push, не переписывать опубликованную историю, не двигать
  опубликованные теги.
- Не выводить токены, секреты и персональные данные.
- Роли: Архитектор и Координатор. Кодер git не выполняет.

## Preflight

```sh
git rev-parse --short HEAD
git status --short
git diff --stat
```

Проверить:

- изменены только ожидаемые файлы, посторонних нет;
- документы обновлены в том же коммите;
- `CHANGELOG.md` содержит запись в `[Unreleased]`;
- новое решение оформлено ADR;
- `dotnet-acceptance` пройден; `check-docs.sh` без WARNING.

## Ветки

- `main` — стабильная ветка.
- Фичи: `feature/3.3-cover-letter`, `feature/3.4-apply`,
  `feature/3.5-chats`.
- Документация и срочные правки: `docs/<slug>`, `fix/<slug>`,
  `chore/<slug>`.
- 3.2a остаётся на `main`; историю не переписывать.
- Ветка создаётся от `main`; PR идёт в `main`; merge и теги — владелец.

## Сообщение коммита

Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `build`, `ci`,
`perf`, `style`. Scope — модуль: `parser`, `storage`, `telegram` и т.п.

Формат:

```text
type(scope): короткая тема до 72 символов

Что изменено и почему. Какие проверки пройдены. Если шаг 3.2a —
метка (этап 3.2a, коммит N).
```

Тема — по-русски допустима, глагол в инфинитиве: «удалить», «добавить».
В теле — что и почему, а не пересказ diff. Не добавлять PII.

## Подготовка коммита

- `git add` — только явные пути; `git add -A` без подтверждения
  не использовать.
- `git diff --cached` — проверить, что в индекс попало только нужное.
- Один логический коммит. Не дробить заранее заданные коммиты 3.2a; если
  diff смешанный — предложить разделение владельцу.
- Не добавлять в коммит локальные файлы: `vacancies.db`, `appsettings.json`,
  `candidate_summary.md`, `resume.txt`, `profile.md`, `samples/`,
  `failed_responses/`, `app.log`.

## Push

```sh
git push origin <branch>
```

- Push только в согласованную ветку; `main` — только владелец или явная
  команда.
- Force-push запрещён.
- После push проверить `git status --short`, `git rev-parse --short
  origin/main` и число коммитов впереди.
- Push и tag — отдельные команды; tag без команды не ставить.

## Теги

Правила вех — в `docs/roadmap.md`, раздел «Вехи и теги». Кратко:

- тег ставится на коммит с описанием вехи и записью в `CHANGELOG.md`;
- `-planning` не переводит этап в `done`;
- опубликованный тег не двигается, уточнения — отдельными коммитами.

## Границы

- `stage-runbook` — порядок этапа; `dotnet-acceptance` — проверки;
  `docs-quality` — качество документов.
- Этот skill не описывает этап и не заменяет приёмку.
- При конфликте правил приоритет у `AGENTS.md` и `docs/roadmap.md`;
  расхождение сообщить владельцу.

## Отчёт

Указать: ветку, сообщение, точные команды, проверки, что запушено и куда,
риски. Если git не выполнялся — написать «команды подготовлены, не выполнены».
