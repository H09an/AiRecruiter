# AGENTS.md

Рамка для агентов, работающих с репозиторием AiRecruiter. Читается автоматически
в каждой сессии OpenCode. Текущее состояние кода — в `git log`, план этапов — в
[`docs/roadmap.md`](docs/roadmap.md), здесь только правила и журнал решений.

## Роли и модели

| Роль | Модель | Задача |
|---|---|---|
| Архитектор (основной) | `openrouter/deepseek/deepseek-v4.1-flash-1017` (через прокси, см. ниже) | ставит задачи, пишет промпты, сверяет факты |
| Архитектор (запасной) | `opencode-go/deepseek-v4.1-flash` | тот же контракт; при исчерпании лимитов основного или сбоях |
| Кодер (основной) | `opencode/nemotron-3.5-super-vl-free` | реализует задачу в своём worktree, пока есть бесплатные лимиты |
| Кодер (запасной) | `opencode-go/glm-5.3-flash` | тот же контракт; после окончания бесплатных лимитов или при проблемах с Nemotron |
| Координатор (основной) | `opencode/deepseek-v4.1-flash-free` | проверяет результат, ведёт процесс с заказчиком, пока есть бесплатные лимиты |
| Координатор (запасной) | `opencode-go/claude-haiku-5.5` | тот же контракт; после окончания бесплатных лимитов или при проблемах с DeepSeek |

Основная и запасная модели одной роли взаимозаменяемы. Переключение между ними
решает владелец. Если работа ведётся через субагента, субагент перед обращением
к модели уточняет у владельца, к какой модели обращаться.

Границы ролей:

- Архитектор не пишет код и не меняет файлы: ставит задачи, готовит промпты,
  сверяет факты.
- Кодер реализует задачу в своём worktree, пишет код и документы по промпту
  Архитектора; промпты для себя не пишет, архитектурные вопросы не решает.
- Координатор не пишет код и документы: проверяет результат, ведёт процесс с
  владельцем, возвращает задачу на доработку.
- Конфликт ролей решает владелец.
- «Владелец» и «заказчик» в этом документе — одно и то же лицо.
- Содержание передачи работы (канал — по правилу «Модели общаются через
  владельца» ниже): Координатор — задача на этап или возврат Архитектору с
  обязательными скиллами; Архитектор — промпт Кодеру с границами, приёмкой и
  строкой `Скиллы:`; Кодер — отчёт Координатору с файлами, тестами, сборкой,
  рисками и результатами проверок по загруженным скиллам.

Обязанности Координатора по документам и приёмке:

- проверяет, что документы обновлены в том же коммите, что и код;
- запускает приёмку: сборка, тесты, формат, `check-docs.sh`, `--parse-samples`,
  `--replay-failed`;
- проверяет, что `CHANGELOG.md`, `docs/architecture.md`, `docs/roadmap.md` и ADR
  согласованы;
- готовит владельцу точные команды `commit`, `tag`, `push` и текст сообщения.

Модель `openrouter/deepseek/deepseek-v4.1-flash-1017` вызывается через прокси.
Прокси задаётся переменными окружения `HTTPS_PROXY` / `HTTP_PROXY` (и
`NO_PROXY`). Адрес прокси и учётные данные не хранятся в репозитории, не
выводятся в логи, отчёты и промпты. Если запрос к основной модели падает на
сетевой ошибке, сначала проверить переменные окружения, затем сообщить
владельцу; переключение на запасную модель — по его решению.

## Правила процесса

- Работать только в текущем рабочем каталоге (worktree). Не переходить в
  основной репозиторий и в другие `AiRecruiter-*`.
- Перед стартом: `git rev-parse --short HEAD` и `git status`. Если не совпадает
  с ожидаемым — остановиться и сообщить.
- Git-операции (`commit`, `tag`, `push`) по умолчанию выполняет владелец.
  Исключение — явная команда заказчика: тогда операцию выполняет агент.
- Модели общаются через владельца: задачи и ответы передаёт владелец. Субагент
  для связи с моделью используется только по прямому разрешению владельца.
- Промпт начинается со строки `Роль: <Архитектор|Кодер|Координатор>` — адресат и
  его контракт. Модель в промпте не указывается: её выбирает владелец по таблице
  ролей. Роль задаёт обязательный минимум скиллов; в `Скиллы:` попадают этот
  минимум и скиллы, нужные по ситуации, с пояснением. Лишние скиллы роли не
  перечисляются. Промпт без `Роль:` не передаётся.
- Не менять существующие тесты без обоснования; новые добавлять.
- Не использовать `!` (null-forgiving), `#pragma`, `NoWarn` ради подавления
  предупреждений.
- Тесты не ходят в сеть и не вызывают GigaChat.
- Приёмка перед отчётом:
  `dotnet build AiRecruiter.slnx -c Release --nologo --no-incremental -p:TreatWarningsAsErrors=true`
  (0/0), `dotnet test AiRecruiter.slnx -c Release --no-build`,
  `dotnet format AiRecruiter.slnx --verify-no-changes --no-restore` (exit 0),
  `--parse-samples tests/Fixtures`, `--replay-failed failed_responses`.
- В логах и отчётах не выводить содержимое `candidate_summary.md`, `resume.txt`,
  `profile.md` и персональные данные.
- `candidate_summary.md`, `resume.txt`, `profile.md`, `samples/`,
  `failed_responses/`, `appsettings.json`, `vacancies.db` — локальные файлы, в
  git не попадают.
- Перед началом каждого этапа модель даёт владельцу полное описание предстоящего
  этапа: что меняется, какие прежние решения устарели, что уже реализовано, и
  вопросы, которые нужно закрыть по контексту. Без этого описание этапа не
  начинается.

## Документация

- Назначение документов:
  - `README.md` — запуск и настройка;
  - `CHANGELOG.md` — что изменилось по этапам;
  - `docs/architecture.md` — текущее состояние кода (поток, модули, статусы,
    схема БД, известные расхождения);
  - `docs/roadmap.md` — этапы, границы, критерии готовности, зависимости и
    риски;
  - `docs/adr/` — почему решено так (ADR).
- Правило: документ меняется в том же коммите, что и код. Коммит без нужного
  обновления документа не принимается; «обновлю после коммита» недопустимо.
- Формат ссылок на код: markdown-ссылка с якорем `#L` на строку (например
  `[Program.cs:194-220](src/AiRecruiter/Program.cs#L194-L220)`); голых записей
  вида `путь:строка` в документах нет.
- Перед изменением потока или БД — прочитать `docs/architecture.md`.
- Формулировки должны быть однозначными. Фраза не должна допускать двух
  прочтений: «отложено до 3.5» и «отклонено навсегда» — разные вещи. Если работа
  отложена, писать «отложено, лежит в бэклоге» и указывать где; если отклонена —
  «не делаем» и почему.
- Один термин — одно значение. Названия статусов, полей и этапов совпадают во
  всех документах; разные слова для одного понятия не используются.
- Термины решений:
  - `сделано` — код и документы уже в репозитории;
  - `план` — в `docs/roadmap.md`, есть этап и границы;
  - `отложено` — в бэклоге или «Вне этапов», нужен отдельный запуск;
  - `не входит в этап` — граница текущего этапа, не отказ от работы;
  - `отклонено` — не делаем; причина записана.
- Чеклист перед коммитом:
  1. Код и `docs/architecture.md` согласованы.
  2. Запись в `CHANGELOG.md` в `[Unreleased]`.
  3. Новое решение — новый ADR в `docs/adr/`.
  4. Статус и критерии этапа в `docs/roadmap.md` обновлены.
  5. `README.md` обновлён при изменении запуска или конфигурации.
  6. `bash scripts/check-docs.sh` — без предупреждений.
  7. Сборка, тесты, формат — без ошибок.
  8. В документах текущего состояния (README, architecture) решение не описано
     как текущее поведение: у нереализованного есть пометка «план, шаг N» или «в
     коде пока нет», у реализованного — ссылка на код.

### Стандарт документации

- Формат: CommonMark, UTF-8, LF, один H1 вне блоков кода, ATX-заголовки; пустая
  строка вокруг заголовков, списков, таблиц и блоков кода.
- Перенос: текст и пункты списков — до 80 символов; таблицы, код, ссылки
  и URL не переносятся.
- Владение фактом — по разделу «Назначение документов» выше. Один факт — один
  владелец; в других документах — краткая выжимка со ссылкой.
- План работ — только в `docs/roadmap.md`. Решение — в ADR или журнале решений.
  Текущее расхождение — в `docs/architecture.md`. Удаление плана допускается
  только как «отклонено» с причиной; потерянных планов нет.
- CHANGELOG — Keep a Changelog 1.1.0: `[Unreleased]`, категории `Добавлено`,
  `Изменено`, `Устарело`, `Удалено`, `Исправлено`, `Безопасность`; изменения
  документации — в `Изменено` с префиксом `Документация:`.
  - `Документация:` — изменены только файлы документации: `README.md`,
    `AGENTS.md`, `CHANGELOG.md`, `SECURITY.md`, `docs/`. Если менялись код,
    `.opencode/`, `scripts/`, CI или тег — метка не ставится, пишется обычный
    пункт.
  - Правило действует для `[Unreleased]` и будущих версий; вышедшие версии не
    переписываются.
- ADR — `Статус`, `Дата`, `Контекст`, `Решение`, `Последствия`;
  `Рассмотренные варианты` — необязательный раздел. Принятое не переписывается,
  а заменяется новым ADR.
- README — что делает, требования, установка и быстрый старт, конфигурация,
  запуск, файлы, диагностика, тесты, разработка, безопасность, лицензия.
- architecture — только текущее состояние: поток, модули, статусы, схема,
  известные расхождения; планов нет.
- roadmap — этап, статус, цель, что входит/не входит, зависимости, DoD, риски;
  статусы `planned` / `in progress` / `done`.
- Сложный шаг roadmap может иметь подраздел «Шаг N — детали»; он не заменяет
  DoD.
- AGENTS — контракт для агентов: роли, права, процесс, журнал решений. Текущее
  состояние здесь не дублируется; планы ссылаются на roadmap.
- Полнота: команды выполнимы, значения по умолчанию и пути указаны, утверждения
  проверяемы; отсылок к чату нет.

## Журнал решений

Журнал фиксирует решения для агентов, а не текущее состояние. Текущее состояние
— `docs/architecture.md`, план — `docs/roadmap.md`, почему — ADR. Плановое
решение должно быть помечено «план» или ссылкой на шаг; сверка пометок — D4.

Формат: что решили — почему.

### Архитектура

- Поиск и разбор карточек остаётся на AngleSharp. Playwright добавляется только
  для откликов и чатов (гибрид), а не заменяет парсер: поиск статичен, тесты на
  фикстурах работают.
- Состояние в SQLite (`Microsoft.Data.Sqlite` + Dapper), а не в
  `seen_vacancies.txt`: нужны статусы, дедуп по работодателю, калибровка.
- Список просмотренных вакансий хранится только в SQLite. Почему: один источник
  правды; файл `seen_vacancies.txt` больше не ведётся; миграция из него ещё есть
  в `Program.cs` и будет удалена в 3.2a; тесты работают на временной БД.
- Все оценки пишутся в БД, включая низкие: без них нельзя калибровать порог.
- Решение этапа 3.2a (в коде пока не реализовано): каждый логический вызов
  GigaChat сохраняется в журнал `llm_calls`. Почему: нужен разбор оценок и
  повторный прогон без обращения к hh.ru. Промпт содержит сводку кандидата,
  поэтому его содержимое не выводится в логи и отчёты.

### Данные и журнал (этап 3.2a)

- Лимит: 4 логических вызова на вакансию — 3 попытки анализа + 1 repair.
  HTTP-повторы внутри вызова в лимит не входят, но фиксируются; 12 HTTP —
  теоретический потолок, не бюджет.
- `purpose` = `analysis` | `repair` | `letter`; письмо (этап 3.3) — отдельный
  лимит. `http_attempts` — число HTTP-запросов внутри логического вызова.
  `repair_used` и `http_calls` отдельными колонками не хранятся: repair виден по
  `purpose`, сумма HTTP — по `http_attempts`. `raw_response` ограничен 64 КБ.
- Repair: инструкция в system-сообщении, предыдущий ответ модели — в user;
  мёртвый параметр `vacancyDescription` удаляется.
- `prompt_versions` хранит system-промпт по `sha256-<16 hex>`,
  `candidate_profiles` — `candidate_summary.md` по hash; в `llm_calls` пишутся
  только `prompt_version` и `candidate_hash`. Почему: промпт и сводка не
  дублируются в каждой строке журнала.
- `attempts` увеличивается при сохранении результата, а не перед анализом;
  `Upsert` и `SetStatus` его не трогают. После 3 неудач ставится
  `analysis_abandoned`; на старте прогона `analysis_failed` с `attempts >= 3`
  переводится в `analysis_abandoned`. Почему: иначе повторная отправка и фильтры
  сбрасывают счётчик.
- `analysis_abandoned` ставится по одному условию: `attempts >= 3` и анализ так
  и не удался. Отсутствие score, комментария и письма, отсутствие сообщения в
  Telegram и прекращение повторов — следствия, а не отдельные условия.
- Возврат `analysis_abandoned`: исправить причину, затем
  `UPDATE vacancies SET attempts = 0, status = 'analysis_failed', fail_reason = NULL WHERE link = '...';`.
  Следующий прогон возьмёт вакансию в анализ, только если она снова появится в
  выдаче; если нет — нужен `--retry-failed` (3.4) или ручной запуск по ссылке.
- Полное описание: `Description.Length <= 6000` — один блок `ПОЛНОЕ ОПИСАНИЕ`;
  длиннее — `ТРЕБОВАНИЯ` и непустые секции; пустой `Description` при непустых
  `Requirements`/`Responsibilities`/`Conditions` — сборка из секций; без
  описания и этих секций — LLM не вызывать, `analysis_failed`. Почему: не терять
  текст вакансии и не платить за пустой вызов.
- `Experience` — белый список значений; fallback по тексту требований не должен
  давать мусор вроде «с системами управления тестированием». Почему: на
  `only_requirements.html` fallback попадает в промпт и Telegram.
- Статусы — константы, не строковые литералы; `seen` остаётся legacy для старых
  строк. Почему: опечатка в строке ломает фильтр, отчёт и `GetLinksToSkip`.
- `main_text_source` — в `llm_calls` (`description` / `requirements`), только
  для `purpose = analysis`.
- `GetLinksToSkip` строится по исключению: не пропускаются `new` и
  `analysis_failed`, всё остальное — терминальные статусы. Почему: новый статус
  не забудут добавить в белый список и вакансия не уйдёт повторно в Telegram.
  (план, шаг 6; сейчас — белый список в `VacancyRepository`).
- `description` в `vacancies` и `raw_response` в `llm_calls` сохраняются только
  для `analysis_failed` / `analysis_abandoned` и для вызовов, которым
  понадобился повтор.
- Telegram: без обрезки текста; длину комментария задаёт правило в промпте.
  Существующая проверка `comment` 10–800 символов —
  [JobAnalyzer.cs:865-880](src/AiRecruiter/Analyzers/JobAnalyzer.cs#L865-L880) —
  остаётся; превышение 4096 символов — отправка вторым сообщением (входит в
  3.2a, в коде пока нет).
- `resume.txt` и `profile.md` в анализе и письме не используются: единственный
  источник — `candidate_summary.md`. Контакты `Contacts:Fio/Tg/Phone/Email` в
  анализ не передаются и пишутся в конце сопроводительного письма —
  [ADR-0011](docs/adr/0011-contacts-in-cover-letter.md).
- `failed_responses/` сохраняется до перехода `--replay-failed` на БД.
- Ретенция `llm_calls` до калибровки — хранить всё.

### Оценка и фильтры

- Жёсткий предфильтр по заголовку до LLM. Стоп-слова: `senior`, `lead`,
  `teamlead`, `тимлид`, `архитектор`, `1с`, `head`, `стажер`, `стажёр`,
  `стажировка`, `интерн`, `intern`, `internship`, `trainee`. Почему стажёрские
  отсекаем: заказчик их не рассматривает.
- `middle` и `middle+` не отсекаются, оценка понижается моделью. Почему:
  кандидат может пройти на middle при сильном профиле.
- Уровень кандидата в код не передаётся. Оценивает модель по
  `candidate_summary.md`. Почему: это единственный источник правды, а числовые
  потолки в C# дублируют суждение, которое должна делать модель.
- Не выводить уровень из общего стажа. Почему: оценивать нужно конкретные роли и
  их содержание из `candidate_summary.md`, а не суммарное число лет.
- `ReclassifyDesirableMissing` определяет обязательность навыка по
  пункту/секции, где он найден, а не по словам «обязательно/желательно» во всём
  описании. Решение 3.2a, в коде пока не реализовано: сейчас маркеры
  обязательности и желательности ищутся по всему тексту требований и описания —
  [JobAnalyzer.cs:1090-1094](src/AiRecruiter/Analyzers/JobAnalyzer.cs#L1090-L1094).
- Порог Telegram `Analyzer:MinScore = 3`. Оценки ниже порога пишутся в лог и в
  БД со статусом `analyzed_low`, в Telegram не отправляются. Метка «🔥
  откликаться» при score ≥ 7, «💭 на подумать» при 3–6. Почему: заказчик снизил
  порог, чтобы увидеть объём оценок 3–6; финальное значение фиксируем после
  калибровки на данных.
- Shadow mode на старте: анализируем всё, в Telegram по порогу. Почему: не
  получить пустой Telegram из-за слишком жёстких фильтров.
- Код-дефолты GigaChat сейчас: `MaxTokens = 800`, модель `GigaChat` —
  [JobAnalyzer.cs:99](src/AiRecruiter/Analyzers/JobAnalyzer.cs#L99),
  [JobAnalyzer.cs:102](src/AiRecruiter/Analyzers/JobAnalyzer.cs#L102). Решение

### Письмо и отклики (этапы 3.3–3.4)

- Письмо и отклик — отдельные фичи, а не основной функционал: флаги
  `Features:CoverLetter` и `Features:Apply`; при выключенной фиче её сетевые
  вызовы не выполняются, её поля остаются пустыми, а запись о вакансии создаётся
  основным потоком в любом случае.
- Отклик без письма не выполняется ни при каких настройках.
  `Features:Apply = true` при `Features:CoverLetter = false` — отклики не
  запускаются, выходит предупреждение с причиной; остальная программа работает.
- Письмо: 4–6 предложений; первое — опыт кандидата под главное требование
  вакансии, а не про компанию. Без длинного тире и стрелок, без зарплатных
  ожиданий, без выдуманных фактов.
- Контакты `Contacts:Fio/Tg/Phone/Email` пишутся в конце сопроводительного
  письма отдельным блоком (ФИО, tg, tel, email) и не попадают ни в анализ, ни в
  `llm_calls`; чтение и проверка контактов на старте остаются. Почему: письмо
  без способа связи бесполезно, а оценщику контакты не нужны —
  [ADR-0011](docs/adr/0011-contacts-in-cover-letter.md).
- Нет `candidate_summary.md` — программа останавливается на старте с ошибкой, до
  парсинга и отправки; путь «отправить без анализа и score» не используется.
  `candidate_hash` всегда считается от реальной сводки.
- Сбой письма: статус `letter_failed`, `cover_letter_done = 0`, код причины
  `letter_fail_reason` и текст `letter_fail_details`; попытка одна, повторов и
  повторной генерации нет, разбор ручной. Отклик не выполняется, карточка с
  сообщением о сбое уходит в Telegram, `letter_failed` входит в
  `GetLinksToSkip`. При успехе `cover_letter_done = 1`, причины пустые.
- Возврат `letter_failed` — только вручную, SQL-сбросом в `status = 'new'`,
  `attempts = 0`, с очисткой `cover_letter`, `cover_letter_done`, причин письма
  и `fail_reason`.
- Отдельного дневного лимита откликов нет: за прогон парсер даёт не больше 10
  новых вакансий, отклик выполняется только для прошедших порог и с готовым
  письмом; на практике около 4 попыток или меньше. Считаются только вакансии с
  попыткой отклика.
- В сообщении о вакансии при включённом `Features:Apply` есть подпись «Отклик
  отправлен» или «Отклик не отправлен» с причиной; при выключенном флаге подписи
  нет. Сообщение уходит после попытки отклика и содержит итоговый статус.
- Одна попытка отклика, повторов нет; результат — `apply_done` и код
  `apply_fail_reason` в записи вакансии (`http_403`, `captcha`, `test_required`,
  `dedup_7d`, `timeout`, `unknown`); при успехе причина пустая. Если письма нет,
  статус остаётся `letter_failed` или `sent`, `apply_done = 0`. Статусы
  `applied`, `apply_failed`, `duplicate_employer`, `needs_test`, `captcha`
  входят в `GetLinksToSkip`.
- `applications` хранит исход отклика: `outcome` (`invited` / `rejected`) и
  `outcome_at`; `silent` вычисляется по возрасту отклика, отдельного поля нет.
- Риск блокировки аккаунта принят заказчиком. Меры: паузы 2,5–6 с, без
  параллельных сессий; при капче и любом 403 — уведомление и остановка прогона,
  без пауз и повторов. Хранение сессии и конкретные меры скрытия автоматизации
  выбираются при реализации 3.4; прогрев, пропуск вакансий и прокси не
  используем.
- Тест или анкета при отклике — не проходить, отправлять ссылку в Telegram.
- Дедуп: повторный отклик на вакансии одного работодателя не чаще чем раз в 7
  дней.
- Чаты: автоответы только на вопросы о стеке, опыте и графике; деньги, переезд,
  личные данные и тестовые — черновик заказчику. Сообщения хранятся с ролью
  (`hr` / `bot` / `owner`), чтобы не отвечать дважды.
- Метрики 3.6 считаются SQL по SQLite; отчёт — `--export-report <path>` в
  Markdown, без API-интеграций и NotebookLM. Аудит генерации — по `llm_calls`,
  отдельный модуль не нужен.

### Процесс и инструменты

- Nemotron через OpenRouter в проекте не используется. Ключ OpenRouter
  используется только ролью Архитектора (основная модель, через прокси); роль
  Кодера работает через провайдер `opencode`.
- Для A/B-сравнений: одинаковый промпт, отдельный worktree от `main`,
  обязательная рамка «работать только в текущем каталоге».
- План этапов вынесен в `docs/roadmap.md`; `AGENTS.md` хранит процесс и журнал
  решений. Почему: у плана отдельный жизненный цикл — статусы, границы, DoD;
  смешение с процессной рамкой мешало приёмке. Решение —
  [ADR-0010](docs/adr/0010-roadmap-separate-document.md).
- Проектные скиллы OpenCode лежат в `.opencode/skills/`: `code-review`,
  `dotnet-acceptance`, `sqlite-migration`, `stage-runbook`, `hh-fixtures`,
  `gigachat-contract`, `audit-triage`. Это рабочие чек-листы, а не источник
  правды и не расширение границ этапа; при расхождении приоритет у `AGENTS.md` и
  `docs/roadmap.md`, расхождение сообщается владельцу.
- Скилл загружается инструментом `skill` по точному ID — имени папки, а не по
  `name` из frontmatter. Владелец или субагент по его поручению может загрузить
  скилл принудительно, указав `@` и ID, например `@code-review`.
- Обязательные точки загрузки:
  - Архитектор: `stage-runbook` — перед описанием этапа и промптом Кодеру по
    этапу; `audit-triage` — при разборе внешнего аудита.
  - Кодер: `stage-runbook` — на старте этапа; `sqlite-migration`, `hh-fixtures`,
    `gigachat-contract` — по области изменений (если затронуто несколько,
    загрузить все); `dotnet-acceptance` — перед отчётом.
  - Координатор: `stage-runbook` — при подготовке задачи Архитектору на этап и
    при закрытии этапа; `code-review` — при проверке diff; `dotnet-acceptance` —
    при приёмке; `audit-triage` — если владелец поручил разбор аудита.
- В задаче на этап Координатор перечисляет Архитектору обязательные скиллы по
  области; в промпте Кодера Архитектор указывает их в строке `Скиллы:` (если
  скиллы не нужны — `Скиллы: нет`). Владелец или субагент по его поручению при
  передаче промпта Кодеру проверяет наличие строки; Координатор при приёмке
  сверяет наличие обязательных скиллов со строкой `Загружены:` в отчёте.
- Кодер указывает в отчёте строку `Загружены:` с ID и результаты проверок по
  ним; если скилл недоступен или не загружен, это указывается явно.
- MCP: только `context7` в `.opencode/opencode.jsonc` — документация библиотек.
  Через него не передаются код, резюме, сводка кандидата, переписка и
  персональные данные.
