# AGENTS.md

Протокол для агентов, работающих с репозиторием AiRecruiter. Читается
автоматически в каждой сессии OpenCode. План этапов —
[`docs/roadmap.md`](docs/roadmap.md), журнал решений —
[`docs/decisions.md`](docs/decisions.md).

## Порядок чтения и preflight

1. `AGENTS.md` — роли, правила, документация, скиллы.
2. [`docs/roadmap.md`](docs/roadmap.md) — этап, границы, DoD.
3. [`docs/architecture.md`](docs/architecture.md) — текущее состояние кода.
4. [`docs/decisions.md`](docs/decisions.md) и ADR по теме — почему решено так.

Перед стартом: `git rev-parse --short HEAD` и `git status --short`. Если HEAD
или состояние дерева не совпадает с ожидаемым — остановиться и сообщить
владельцу. При расхождении `AGENTS.md`, roadmap, decisions и ADR — остановиться
и сообщить владельцу, трактовку не выбирать самостоятельно.

## Роли и модели

| Роль | Модель | Задача |
|---|---|---|
| Архитектор | `openrouter/deepseek/deepseek-v4.1-flash-1017` (через прокси, см. ниже) | ставит задачи, пишет промпты, сверяет факты |
| Кодер | `opencode-go/glm-5.3-flash` | реализует задачу в текущем каталоге, пишет код и документы по промпту |
| Координатор | `opencode-go/claude-haiku-5-5` | проверяет результат, ведёт процесс с заказчиком |

У каждой роли одна модель. Смена модели — только по решению владельца.
Если работа ведётся через субагента, он перед обращением уточняет у
владельца, к какой модели обращаться.

Границы ролей:

- Архитектор не пишет код и не меняет файлы: ставит задачи, готовит промпты,
  сверяет факты.
- Кодер реализует задачу в текущем каталоге, пишет код и документы по промпту
  Архитектора; промпты для себя не пишет, архитектурные вопросы не решает.
- Координатор не пишет код и документы: проверяет результат, ведёт процесс с
  владельцем, возвращает задачу на доработку.
- Конфликт ролей решает владелец.
- «Владелец» и «заказчик» в этом документе — одно и то же лицо.
- Содержание передачи работы (канал — по правилу «Модели общаются через
  владельца» ниже): Координатор — задача на этап или возврат Архитектору с
  обязательными скиллами; Архитектор — промпт Кодеру с границами, приёмкой и
  строкой `Скиллы:`; Кодер — отчёт Координатору с файлами, тестами, сборкой,
  рисками и результатами проверок по загруженным скиллам.

Обязанности Координатора по документам и приёмке:

- проверяет, что документы обновлены в том же коммите, что и код;
- запускает приёмку: сборка, тесты, формат, `check-docs.sh`, `--parse-samples`,
  `--replay-failed`;
- проверяет, что `CHANGELOG.md`, `docs/architecture.md`, `docs/roadmap.md` и ADR
  согласованы;
- готовит владельцу точные команды `commit`, `tag`, `push` и текст сообщения.

Модель `openrouter/deepseek/deepseek-v4.1-flash-1017` вызывается через прокси.
Прокси задаётся переменными окружения `HTTPS_PROXY` / `HTTP_PROXY` (и
`NO_PROXY`). Адрес прокси и учётные данные не хранятся в репозитории, не
выводятся в логи, отчёты и промпты. Если запрос к модели Архитектора падает на
сетевой ошибке, сначала проверить переменные окружения, затем сообщить
владельцу.

Ключ OpenRouter используется только ролью Архитектора
(`openrouter/deepseek/deepseek-v4.1-flash-1017`, через прокси); Кодер и
Координатор работают через провайдер `opencode-go`.

## Правила процесса

- Работать только в текущем рабочем каталоге. Не переходить в другие
  `AiRecruiter-*`. A/B-сравнения через отдельные worktree и ветки не
  используются: Кодер работает в текущем каталоге.
- Git-операции (`commit`, `tag`, `push`) по умолчанию выполняет владелец.
  Исключение — явная команда заказчика: тогда операцию выполняет агент.
- Модели общаются через владельца: задачи и ответы передаёт владелец. Субагент
  для связи с моделью используется только по прямому разрешению владельца.
- Промпт начинается со строки `Роль: <Архитектор|Кодер|Координатор>` — адресат и
  его контракт. Модель в промпте не указывается: она указана в таблице ролей;
  менять её может только владелец. Роль задаёт обязательный минимум скиллов; в
  `Скиллы:` попадают этот минимум и скиллы, нужные по ситуации, с пояснением.
  Лишние скиллы роли не перечисляются. Промпт без `Роль:` не передаётся.
- Не менять существующие тесты без обоснования; новые добавлять.
- Не использовать `!` (null-forgiving), `#pragma`, `NoWarn` ради подавления
  предупреждений.
- Тесты не ходят в сеть и не вызывают GigaChat.
- Статусы вакансий — константы `VacancyStatus`, не строковые литералы; `seen`
  остаётся legacy для старых строк.
- Приёмка перед отчётом:
  `dotnet build AiRecruiter.slnx -c Release --nologo --no-incremental -p:TreatWarningsAsErrors=true`
  (0/0), `dotnet test AiRecruiter.slnx -c Release --no-build`,
  `dotnet format AiRecruiter.slnx --verify-no-changes --no-restore` (exit 0),
  `--parse-samples tests/Fixtures`, `--replay-failed failed_responses`.
- В логах и отчётах не выводить содержимое `candidate_summary.md`, `resume.txt`,
  `profile.md` и персональные данные.
- `candidate_summary.md`, `resume.txt`, `profile.md`, `samples/`,
  `failed_responses/`, `appsettings.json`, `vacancies.db` — локальные файлы, в
  git не попадают.
- Перед началом каждого этапа модель даёт владельцу полное описание предстоящего
  этапа: что меняется, какие прежние решения устарели, что уже реализовано, и
  вопросы, которые нужно закрыть по контексту. Без этого описание этапа не
  начинается.

## Документация

- Назначение документов:
  - `README.md` — запуск и настройка;
  - `CHANGELOG.md` — что изменилось по этапам;
  - `docs/architecture.md` — текущее состояние кода (поток, модули, статусы,
    схема БД, известные расхождения);
  - `docs/roadmap.md` — этапы, границы, критерии готовности, зависимости и
    риски;
  - `docs/decisions.md` — журнал процессных решений и указатели на ADR;
  - `docs/adr/` — почему решено так (ADR).
- Правило: документ меняется в том же коммите, что и код. Коммит без нужного
  обновления документа не принимается; «обновлю после коммита» недопустимо.
- Объём `AGENTS.md` — до 250 строк. При превышении «Стандарт документации»
  выносится в `docs/documentation.md`, в `AGENTS.md` остаётся ссылка.
- Формат ссылок на код: markdown-ссылка с якорем `#L` на строку (например
  `[Program.cs:198-199](src/AiRecruiter/Program.cs#L198-L199)`); голых записей
  вида `путь:строка` в документах нет. При изменении кода перепроверять, что
  строка по ссылке соответствует тексту: `check-docs.sh` проверяет путь и
  якорь, но не содержимое.
- Перед изменением потока или БД — прочитать `docs/architecture.md`.
- Формулировки должны быть однозначными. Фраза не должна допускать двух
  прочтений: «отложено до 3.5» и «отклонено навсегда» — разные вещи. Если работа
  отложена, писать «отложено, лежит в бэклоге» и указывать где; если отклонена —
  «не делаем» и почему.
- Один термин — одно значение. Названия статусов, полей и этапов совпадают во
  всех документах; разные слова для одного понятия не используются.
- Термины решений:
  - `сделано` — код и документы уже в репозитории;
  - `план` — в `docs/roadmap.md`, есть этап и границы;
  - `отложено` — в бэклоге или «Вне этапов», нужен отдельный запуск;
  - `не входит в этап` — граница текущего этапа, не отказ от работы;
  - `отклонено` — не делаем; причина записана.
- Чеклист перед коммитом:
  1. Код и `docs/architecture.md` согласованы.
  2. Запись в `CHANGELOG.md` в `[Unreleased]`.
  3. Новое архитектурное решение — новый ADR в `docs/adr/`; процессное — запись
     в `docs/decisions.md`.
  4. Статус и критерии этапа в `docs/roadmap.md` обновлены.
  5. `README.md` обновлён при изменении запуска или конфигурации.
  6. `bash scripts/check-docs.sh` — без предупреждений.
  7. Сборка, тесты, формат — без ошибок.
  8. В документах текущего состояния (README, architecture) решение не описано
     как текущее поведение: у нереализованного есть пометка «план, шаг N» или «в
     коде пока нет», у реализованного — ссылка на код.

### Стандарт документации

- Формат: CommonMark, UTF-8, LF, один H1 вне блоков кода, ATX-заголовки; пустая
  строка вокруг заголовков, списков, таблиц и блоков кода.
- Перенос: текст и пункты списков — до 80 символов; таблицы, код, ссылки и URL
  не переносятся.
- Владение фактом — по разделу «Назначение документов» выше. Один факт — один
  владелец; в других документах — краткая выжимка со ссылкой.
- План работ — только в `docs/roadmap.md`. Решение — в ADR или
  `docs/decisions.md`. Текущее расхождение — в `docs/architecture.md`.
  Удаление плана допускается только как «отклонено» с причиной; потерянных
  планов нет.
- CHANGELOG — Keep a Changelog 1.1.0: `[Unreleased]`, категории `Добавлено`,
  `Изменено`, `Устарело`, `Удалено`, `Исправлено`, `Безопасность`; изменения
  документации — в `Изменено` с префиксом `Документация:`.
  - `Документация:` — изменены только файлы документации: `README.md`,
    `AGENTS.md`, `CHANGELOG.md`, `SECURITY.md`, `docs/`. Если менялись код,
    `.opencode/`, `scripts/`, CI или тег — метка не ставится, пишется обычный
    пункт.
  - Правило действует для `[Unreleased]` и будущих версий; вышедшие версии не
    переписываются.
- ADR — `Статус`, `Дата`, `Контекст`, `Решение`, `Последствия`;
  `Рассмотренные варианты` — необязательный раздел. Принятое не переписывается,
  а заменяется новым ADR.
- README — что делает, требования, установка и быстрый старт, конфигурация,
  запуск, файлы, диагностика, тесты, разработка, безопасность, лицензия.
- architecture — только текущее состояние: поток, модули, статусы, схема,
  известные расхождения; планов нет.
- roadmap — этап, статус, цель, что входит/не входит, зависимости, DoD, риски;
  статусы `planned` / `in progress` / `done`.
- Сложный шаг roadmap может иметь подраздел «Шаг N — детали»; он не заменяет
  DoD.
- AGENTS — протокол для агентов: роли, права, процесс, документация и скиллы;
  журнал решений — `docs/decisions.md`. Текущее состояние здесь не дублируется;
  планы ссылаются на roadmap.
- Полнота: команды выполнимы, значения по умолчанию и пути указаны, утверждения
  проверяемы; отсылок к чату нет.

## Скиллы

- Проектные скиллы OpenCode лежат в `.opencode/skills/`: `code-review`,
  `docs-quality`, `dotnet-acceptance`, `git-workflow`, `sqlite-migration`,
  `stage-runbook`, `hh-fixtures`, `gigachat-contract`, `audit-triage`. Это
  рабочие чек-листы, а не источник правды и не расширение границ этапа; при
  расхождении приоритет у `AGENTS.md` и `docs/roadmap.md`, расхождение
  сообщается владельцу.
- Скилл загружается инструментом `skill` по точному ID — имени папки, а не по
  `name` из frontmatter. Владелец или субагент по его поручению может загрузить
  скилл принудительно, указав `@` и ID, например `@code-review`.
- Обязательные точки загрузки:
  - Архитектор: `stage-runbook` — перед описанием этапа и промптом Кодеру по
    этапу; `audit-triage` — при разборе внешнего аудита; `git-workflow` — при
    commit/tag/push по явной команде; `docs-quality` — при проверке документов
    и ADR.
  - Кодер: `stage-runbook` — на старте этапа; `sqlite-migration`, `hh-fixtures`,
    `gigachat-contract` — по области изменений (если затронуто несколько,
    загрузить все); `docs-quality` — при изменении документов;
    `dotnet-acceptance` — перед отчётом.
  - Координатор: `stage-runbook` — при подготовке задачи Архитектору на этап и
    при закрытии этапа; `code-review` — при проверке diff; `git-workflow` — при
    подготовке и выполнении commit/tag/push; `docs-quality` — при приёмке
    документов; `dotnet-acceptance` — при приёмке; `audit-triage` — если
    владелец поручил разбор аудита.
- Роль загружает только скиллы своей матрицы: скилл вне её не загружается,
  расхождение с промптом сообщается владельцу до начала работы.
- При передаче промпта Кодеру проверяется, что в `Скиллы:` только скиллы его
  матрицы; лишний скилл — вернуть автору промпта, работу не начинать.
- В задаче на этап Координатор перечисляет Архитектору обязательные скиллы по
  области; в промпте Кодера Архитектор указывает их в строке `Скиллы:` (если
  скиллы не нужны — `Скиллы: нет`). Владелец или субагент по его поручению при
  передаче промпта Кодеру проверяет наличие строки; Координатор при приёмке
  сверяет наличие обязательных скиллов со строкой `Загружены:` в отчёте.
- Кодер указывает в отчёте строку `Загружены:` с ID и результаты проверок по
  ним; если скилл недоступен или не загружен, это указывается явно.
- MCP: только `context7` в `.opencode/opencode.jsonc` — документация библиотек.
  Через него не передаются код, резюме, сводка кандидата, переписка и
  персональные данные.
