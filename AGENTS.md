# AGENTS.md

Рамка для агентов, работающих с репозиторием AiRecruiter. Читается автоматически в каждой сессии OpenCode.
Текущее состояние кода — в `git log`, здесь только правила и журнал решений.

## Роли и модели

| Роль | Модель | Задача |
|---|---|---|
| Архитектор | `opencode-go/deepseek-v4.1-flash` | ставит задачи, пишет промпты, сверяет факты |
| Кодер (основной) | `opencode/nemotron-3.5-super-vl-free` | реализует задачу в своём worktree, пока есть бесплатные лимиты |
| Кодер (запасной) | `opencode-go/glm-5.3-flash` | тот же контракт; после окончания бесплатных лимитов или при проблемах с Nemotron |
| Координатор | `opencode-go/claude-haiku-5.5` | проверяет результат, ведёт процесс с заказчиком |

Кодер не пишет промпты для себя и не решает архитектурных вопросов.

## Правила процесса

- Работать только в текущем рабочем каталоге (worktree). Не переходить в основной репозиторий и в другие `AiRecruiter-*`.
- Перед стартом: `git rev-parse --short HEAD` и `git status`. Если не совпадает с ожидаемым — остановиться и сообщить.
- Не делать `commit`, `tag`, `push` без явной команды заказчика.
- Не менять существующие тесты без обоснования; новые добавлять.
- Не использовать `!` (null-forgiving), `#pragma`, `NoWarn` ради подавления предупреждений.
- Тесты не ходят в сеть и не вызывают GigaChat.
- Приёмка перед отчётом: `dotnet build AiRecruiter.slnx -c Release --nologo --no-incremental -p:TreatWarningsAsErrors=true` (0/0), `dotnet test AiRecruiter.slnx -c Release --no-build`, `dotnet format AiRecruiter.slnx --verify-no-changes --no-restore` (exit 0), `--parse-samples tests/Fixtures`, `--replay-failed failed_responses`.
- В логах и отчётах не выводить содержимое `candidate_summary.md`, `resume.txt`, `profile.md` и персональные данные.
- `candidate_summary.md`, `resume.txt`, `profile.md`, `samples/`, `failed_responses/`, `appsettings.json` — локальные файлы, в git не попадают.

## Журнал решений

Формат: что решили — почему.

### Архитектура
- Поиск и разбор карточек остаётся на AngleSharp. Playwright добавляется только для откликов и чатов (гибрид), а не заменяет парсер: поиск статичен, тесты на фикстурах работают.
- Состояние в SQLite (`Microsoft.Data.Sqlite` + Dapper), а не в `seen_vacancies.txt`: нужны статусы, дедуп по работодателю, калибровка.
- Все оценки пишутся в БД, включая низкие: без них нельзя калибровать порог.

### Оценка и фильтры
- Жёсткий предфильтр по заголовку до LLM. Стоп-слова: `senior`, `lead`, `teamlead`, `тимлид`, `архитектор`, `1с`, `head`, `стажер`, `стажёр`, `intern`, `trainee`. Почему стажёрские отсекаем: заказчик их не рассматривает.
- `middle` и `middle+` не отсекаются, оценка понижается моделью. Почему: кандидат может пройти на middle при сильном профиле.
- Уровень кандидата в код не передаётся. Оценивает модель по `candidate_summary.md`. Почему: это единственный источник правды, а числовые потолки в C# дублируют суждение, которое должна делать модель.
- Не выводить уровень из общего стажа. Почему: оценивать нужно конкретные роли и их содержание из `candidate_summary.md`, а не суммарное число лет.
- Порог Telegram `Analyzer:MinScore = 7`. Оценки 4–6 только в лог, ниже 4 — в БД со статусом `analyzed_low`. Почему: порог фиксируем после калибровки на данных.
- Shadow mode на старте: анализируем всё, в Telegram по порогу. Почему: не получить пустой Telegram из-за слишком жёстких фильтров.

### Отклики (этап 3.4)
- Лимит 10–12 откликов в день на старте, при необходимости поднимается позже.
- Риск блокировки аккаунта принят заказчиком. Меры: паузы 2,5–6 с, остановка при капче, без параллельных сессий.
- Тест или анкета при отклике — не проходить, отправлять ссылку в Telegram.
- Письмо: 4–6 предложений; первое — опыт кандидата под главное требование вакансии, а не про компанию. Без длинного тире и стрелок, без зарплатных ожиданий, без выдуманных фактов.
- Дедуп: повторный отклик на вакансии одного работодателя не чаще чем раз в 7 дней.
- Чаты: автоответы только на вопросы о стеке, опыте и графике; деньги, переезд, личные данные и тестовые — черновик заказчику.

### Процесс и инструменты
- Nemotron через OpenRouter в проекте не используется. Лимиты ключа OpenRouter не трогаем, пока не решено иначе.
- Для A/B-сравнений: одинаковый промпт, отдельный worktree от `main`, обязательная рамка «работать только в текущем каталоге».

## Этапы

- **3.1 — ядро:** стоп-слова, порог и shadow mode, SQLite, правило уровня в промпте.
- **3.2 — калибровка:** 1–2 недели прогонов, фиксация порога и стоп-листа по данным.
- **3.3 — письмо:** генерация и постобработка, только для `score >= порога`.
- **3.4 — отклики:** Playwright, тест-детект, дедуп по работодателю, 10–12 в день.
- **3.5 — чаты:** чтение и безопасные ответы, черновики заказчику.
- **3.6 — метрики:** конверсия, отклики в день, ошибки.
