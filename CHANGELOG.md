# Changelog

Все заметные изменения проекта AiRecruiter.
Формат основан на [Keep a Changelog 1.1.0](https://keepachangelog.com/ru/1.1.0/).
Версии соответствуют этапам проекта; SemVer не используется.

## [Unreleased]
<!-- Следующий этап: добавьте записи сюда до тега. -->

### Изменено
- Порог Telegram `Analyzer:MinScore` снижен с 7 до 3 (решение заказчика):
  в Telegram уходят оценки 3–10, «💭 на подумать» — при 3–6, «🔥 откликаться» — при 7 и выше;
  `analyzed_low` — только оценки ниже 3.
- Новый ADR-0009: порог `Analyzer:MinScore = 3` (заменяет ADR-0007 в части значения);
  в ADR-0007 статус переведён в «Заменено ADR-0009».

### Документация
- Добавлены проектные скиллы OpenCode: `code-review`, `dotnet-acceptance`,
  `sqlite-migration`, `stage-runbook`, `hh-fixtures`, `gigachat-contract`,
  `audit-triage`.
- `thermo-nuclear-code-review` добавлен в технический бэклог после 3.6:
  жёсткий maintainability-аудит, запуск вручную и findings только в бэклог.
  Скилл `agent-review-prompt` не берём: нет канонического источника и версии.
- Подключён MCP `context7` в `.opencode/opencode.jsonc` для документации
  библиотек; код и персональные данные через него не передаются.
- `AGENTS.md`: зафиксированы границы ролей — Архитектор не пишет код, Кодер
  пишет код и документы по промпту, Координатор проверяет и не пишет код;
  добавлена суброль Координатора «документы и приёмка» (проверки и подготовка
  git-команд, git выполняет владелец); «владелец» и «заказчик» — одно лицо.
- Тег `stage-3.2a-planning`: планирование 3.2a завершено — roadmap 3.1–3.6,
  ADR-0010, AGENTS, CHANGELOG, флаги письма/отклика, технический бэклог. Этап
  3.2a не закрыт, код 3.2a не начат.
- Добавлен [`docs/roadmap.md`](docs/roadmap.md): этапы 3.1–3.6, порядок
  `3.1 → 3.2a → 3.2 → 3.3 → 3.4 → 3.5 → 3.6`, границы, критерии готовности,
  зависимости, риски, правила обновления и согласованный порядок работ 3.2a —
  восемь шагов (порог `Analyzer:MinScore` — отдельный коммит вне их).
- `docs/roadmap.md` сверен со всей перепиской: добавлены `SaveAnalysisAttempt`,
  отказ от транзитного `analyzing`, лимит `raw_response` 64 КБ, `kind` в
  `prompt_versions`, repair с инструкцией в system, `--retry-failed` в 3.4,
  сброс `analyzed_low` / `filtered_*` в 3.2, `chat_messages` в 3.5 и метрика
  пропусков по дедупу в 3.6. Уточнены ключ `llm_calls`
  `(link, purpose, attempt_no, call_no)` и поля `chat_messages`.
- Письмо и отклики вынесены в отдельные фичи с флагами `Features:CoverLetter`
  и `Features:Apply` (по умолчанию выключены): отклик без письма не
  выполняется, несовместимая комбинация даёт предупреждение только в Telegram,
  программа продолжает работу без откликов; добавлены `letter_failed`,
  `cover_letter_done`, `apply_done`, коды причин `letter_fail_reason` /
  `apply_fail_reason`, подпись «отклик отправлен / не отправлен» в сообщении о
  вакансии; отдельного дневного лимита нет — отклики ограничены числом новых
  вакансий за прогон и считаются только по попыткам отклика.
- Запись о вакансии создаётся после фильтров и до анализа со статусом `new`,
  после отправки меняется на `sent` (кроме `letter_failed` и статусов
  отклика); при отсутствии `candidate_summary.md` программа останавливается
  на старте, парсинга и отправки нет.
- При капче и любом 403 — уведомление и остановка прогона, без пауз и повторов.
- Зафиксирован ручной возврат `analysis_abandoned` в работу (SQL-сброс
  `attempts` и статуса) и `letter_failed` (SQL-сброс в `new` с очисткой
  письма и причин); отдельных команд нет.
- Код-дефолты GigaChat подняты в плане до `MaxTokens = 1200` и
  `GigaChat-2-Pro`, README приводится к ним.
- Конкретные меры скрытия автоматизации и хранение сессии hh.ru решаются при
  реализации 3.4; точный состав ключей `filters.yaml` — при старте этапа
  пользовательских фильтров.
- В план 3.4 добавлены `applications.outcome` (`invited` / `rejected`) и
  `outcome_at`, `silent` вычисляется по возрасту отклика; в 3.5 —
  роль сообщения (`hr` / `bot` / `owner`); в 3.6 — SQL-метрики и
  `--export-report <path>` без внешних API.
- В 3.2a добавлен фикс `ReclassifyDesirableMissing`: обязательность навыка
  определяется по пункту/секции, где он найден, а не по словам во всём тексте.
- Добавлен технический бэклог после 3.6: декомпозиция и DI, офлайн-тесты с
  `HttpMessageHandler`, надёжность поиска, автоматический повтор анализа,
  пересмотр `MinScore`, политика `score/weighted`, exit code. Это очередь на
  рассмотрение, а не обязательства.
- В правила добавлена однозначность формулировок: отдельные термины для
  «сделано / план / отложено / не входит в этап / отклонено», один термин —
  одно значение, каждый отложенный пункт лежит в бэклоге или «Вне этапов».
- Правило процесса: перед началом каждого этапа модель даёт полное описание
  этапа, отмечает устаревшие решения и задаёт вопросы владельцу.
- Запланирован этап после 3.6: фильтры в `filters.yaml` (YamlDotNet), пример
  `filters.example.yaml` с комментариями, инструкция `docs/filters.md`, чтение
  примера при отсутствии рабочего файла, удаление фильтров из
  `appsettings.example.json`; `GetLinksToSkip` и проверка описания пока
  остаются в коде.
- `AGENTS.md`: раздел «Этапы» заменён ссылкой на roadmap, порядок этапов
  исправлен; в чек-лист добавлена проверка статуса этапа.
- `AGENTS.md`: в журнал решений добавлены `prompt_versions`, `candidate_profiles`,
  инкремент `attempts` при сохранении, правило полного описания, белый список
  `Experience` и статусы-константы.
- Добавлен [`docs/adr/0010-roadmap-separate-document.md`](docs/adr/0010-roadmap-separate-document.md):
  план этапов ведётся в отдельном документе.
- `README.md`: в структуре репозитория указан `docs/roadmap.md`.
- Добавлен `docs/architecture.md`: текущее состояние кода — поток одного прогона,
  модули, статусы, схема БД, известные расхождения с решениями.
- Добавлены `docs/adr/0001`–`0008`: решения задним числом в формате MADR-lite
  (SQLite, `employer_id`, модель GigaChat, `MaxTokens`, стоп-слова, гибридный
  парсер, порог и shadow mode, уровень кандидата).
- `AGENTS.md`: раздел «Документация» с правилом «документ в том же коммите, что
  и код», формат ссылок на код и чеклист перед коммитом; в журнале решений —
  подраздел «Данные и журнал (этап 3.2a)».
- `README.md` приведён к коду: состояние в `vacancies.db` вместо
  `seen_vacancies.txt`, значения по умолчанию модели и `MaxTokens`,
  фактическое число тестов.
- Добавлен `scripts/check-docs.sh`: предупреждения о необновлённой документации,
  битых ссылках на код, битых обычных ссылках и голых записях пути со строками;
  вызов добавлен в `lefthook.yml` (pre-commit) и в CI (шаг «Docs check»).

## [3.1] - 2026-11-17

### Добавлено
- Предфильтр вакансий по зарплате (`Filters:MinSalary`).
- Предфильтр по стоп-словам в заголовке до GigaChat (`Filters:ExcludeTitleWords`).
- Порог оценки `Analyzer:MinScore` и калибровочная статистика (гистограмма в `[ИТОГ]`).
- Состояние вакансий в SQLite (`vacancies.db`) с миграцией из `seen_vacancies.txt`.
- Повтор отправки из сохранённого результата (`send_failed`, `analyzed_ok`) без повторного анализа.
- Колонки `comment`, `cover_letter`, `tech_stack` в таблице `vacancies`.

### Изменено
- Фильтр стажировок перенесён из `TelegramNotifier` в предфильтр по заголовку.
- `analysis_failed` не блокирует вакансию: она переанализируется при следующем появлении в выдаче.
- Правило в промпте оценки: не выводить уровень кандидата из общего стажа.
- Лимит сводки кандидата `candidate_summary.md` поднят до 4000 символов.
- Ужесточён разбор чисел в `SalaryFilter`: группы по три цифры, без склейки соседних чисел.
- Добавлен `AGENTS.md`: рамка процесса для агентов и журнал решений.
